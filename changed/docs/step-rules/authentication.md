# Private authentication

Covers: authentication

1. `AuthService` owns Better Auth 1.7.7 and its separate private SQLite database. `makeAuthLayer` accepts the configured origin, a redacted secret of at least 32 characters, and an absolute `auth.sqlite` path. Its Effect layer requires filesystem and path services. It creates missing auth tables before the service becomes available and closes its Kysely connection when the scope closes.
2. The HTTP adapter accepts only `POST /auth/sign-in/email`, `POST /auth/sign-out`, `GET /auth/get-session`, `GET /auth/sign-in-options`, and, only when email-only sign-in is enabled, `POST /auth/sign-in/judge`. It rejects all other paths and methods. `GET /auth/sign-in-options` returns the shared `SignInOptions` (`password` or `email`, and whether an access code is required) without calling Better Auth. Better Auth also disables email signup. The outer gateway independently owns route admission, response security headers, body limits, and CSRF checks for application and Mastra routes.
3. Email-only sign-in is off by default and enabled only by `AMUSEME_JUDGE_SIGN_IN=true`. It is the `amuseme-judge-sign-in` Better Auth plugin endpoint, so Better Auth's origin/CSRF checks, database rate limiter, session creation and cookies apply. The body is `{ email, accessCode? }`. When `AMUSEME_JUDGE_ACCESS_CODE` is set, a missing or different code returns 401 before any lookup; the comparison does not stop early. The email is trimmed, lowercased and must be a single address of at most 254 characters, otherwise 400. An unknown email creates a user with role `user` and no credential account; a known email signs in only if that user has role `user` and no linked account. Invited password accounts and admins return 403 and never get a session this way. Request role, name and owner fields are ignored. Anyone who knows an email-only address can open that account; this deliberately trades account secrecy for frictionless judge access, so these accounts hold only their own uploads and read-only examples. Password sign-up stays disabled.
4. Invited users enter through the local `scripts/provision-user.ts` command, which invokes Better Auth's server-only `createUser` API without request headers. Roles are exactly `user` or `admin` and come from that command. No registration, recovery, email, impersonation, or admin-management endpoint is public.
5. Session checks read the database on every request and decode the result through the shared domain `Session` schema. Cookie caching is disabled. Expiration, sign-out, deleted sessions, and changed roles take effect on the next read. Missing credentials produce `null`. SDK failures produce `AuthError`, never an authenticated or empty successful fallback.
6. The origin is explicit, has no path or credentials, and uses HTTPS except for HTTP on localhost or an IP loopback address. HTTPS requires Secure cookies. All session cookies are HttpOnly and SameSite=Lax. Trusted origins contain only that origin. Forwarded host, protocol, and client-IP headers have no authority.
7. Better Auth owns retry-free credential verification and database-backed rate limiting. Password sign-in permits ten attempts per rolling minute; email-only sign-in permits twenty. With no verified client-IP source, Better Auth uses one shared per-path bucket, which survives restart. This intentionally limits all invited users together. No claim of per-account or per-client limits is made.
8. POST requests require the exact configured Origin, including before the user has a cookie. The adapter buffers at most 16 KiB with a five-second deadline before calling Better Auth. Effect interruption cancels the body reader, with one second allowed for reader cleanup. Oversized bodies return 413, slow bodies return 408, and unreadable bodies return 400. Better Auth and Kysely Promise APIs are the SDK boundary. Local operations are uninterruptible until their Promise settles because these APIs do not cancel SQLite queries or password hashing. Scope cleanup cannot close the database while an admitted SDK operation is still running. The server owns bounded shutdown. There are no model calls, telemetry events, or application retries.
9. The database file has mode 0600 and its dedicated parent directory has mode 0700. Session tokens, passwords, and secrets never enter application logs or CLI output. Provisioning errors print a fixed message. The CLI requires `AMUSEME_ORIGIN`, `BETTER_AUTH_SECRET`, `AMUSEME_DATA_DIR`, `AMUSEME_INVITE_EMAIL`, `AMUSEME_INVITE_NAME`, `AMUSEME_INVITE_PASSWORD`, and `AMUSEME_INVITE_ROLE`. The database is `auth.sqlite` inside that directory.
10. Tests use real temporary SQLite files and the actual Better Auth handler. They prove email-only sign-in off by default, normalization, account reuse, bad emails, access codes, refusal of password/admin accounts, its rate limit, invited-user roles, invalid passwords, denied registration and role changes, database revocation and expiry, cookie flags, origin restrictions, limiter persistence, and scoped reopening. The manager separately verifies integrated routes and Chrome behavior.

The implementation follows the installed public interfaces and the Better Auth [database](https://better-auth.com/docs/concepts/database), [options](https://better-auth.com/docs/reference/options), and [admin API](https://better-auth.com/docs/plugins/admin) documentation. The request adapter deliberately keeps the admin plugin's HTTP endpoints private while retaining its supported server API for invitations.
