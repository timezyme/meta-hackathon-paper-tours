# Bounded run recovery and explicit retries

Covers: `run.recovery`, `RunRecovery.requestRetry`, `ProviderGuard.retryInput`, provider retrieval, and expired-claim adoption.

1. An expired worker lease does not authorize a second provider submission. Reclaim safe still-running work with a fresh fenced claim, preserving its run ID, workflow ID, start time, deadline, source, and configuration. The manager reopens the saved Mastra snapshot with a new private permit. Completed stage/page receipts and pending local validation reuse saved bytes. Only a prepared attempt with no dispatch marker may be adopted for its first submission.
2. Unretrievable unknown completion stays interrupted. A user retry creates a new run/workflow association through an authenticated owner-scoped request, with an explicit acknowledgment of possible repeated work when needed. This applies to Meta extraction as well as the later Meta stages; its nested model configuration does not imply a retrievable extraction job. Non-Meta extraction keeps its historical resubmission prohibition, and live non-Meta run retries are denied. Persist the request, new queue entry, and exact attempt authorizations atomically. Request keys are idempotent; concurrent requests cannot fork the same prior run.
3. Retry authorizations bind prior attempt, complete input fingerprint, stage/unit, target run, owner, document, and acknowledgment. The guard resolves and consumes these durable records in the same transaction as its new attempt and reservation. Caller-supplied authorization strings alone grant nothing. Invalid model output and permanent input failures do not receive a retry authorization. Confirmed complete transient Meta responses, including extraction, may receive one explicit bounded retry; HTTP transports do not retry POST. A saved pending response replays local validation without a new generation or reservation.
4. Keep the original configured policy and budget identity. All known costs and uncertain reservations across the document's retry chain count against its unchanged cap and the existing global ledger. Provider attempt limits apply across that chain, not separately to each new run. Explicit retry runs are also bounded, even when local failures prepared no provider attempt: allow at most the original `maxProviderAttempts` retry runs, capped at 999 so the initial run plus retries fits the retention service's 1000-snapshot limit. Idempotent replay does not consume another run. Never refund uncertain completion.
5. MinerU retrieval uses its saved attempt UUID and GET only. A fresh claim fences old writers; retrieved bytes settle the same receipt and reservation. Unknown 404/503 remains unresolved. Remote expired/deleted 410 is permanent. No recovery or timeout repeats POST or changes the job UUID.
6. Before local deletion/expiry removes provider attempts, enqueue MinerU extraction attempt UUIDs in `remote_cleanup` in the same transaction. The manager performs remote authenticated deletion and clears only confirmed 204/404 outcomes; an active 409 stays pending. This module makes no cleanup HTTP calls.
7. Tests exercise restart, stale and duplicate claims, per-page replay, concurrent retry requests, authorization forgery/reuse, unknown acknowledgment, late results, retrieval without POST, unchanged budgets, limits, permanent rejection, local failures, and cleanup capture. HTTP/lifecycle/Chrome integration remains manager-owned.

Historical policy reconciliation is an explicit operator action. Version-three rows do not contain the complete original guard policy. Keep new dispatch blocked for them; completed saved responses remain readable. Before any manual binding, stop processing, preserve a database backup, identify the exact original source/configuration and authorized policy from the saved deployment snapshot, and verify every receipt's owner/document/source/version/model configuration plus every attempt's reservation, actual charge, and budget-ledger identity against that snapshot. A current environment file or guessed default is insufficient evidence. If the original policy cannot be established, leave new dispatch blocked. This migration does not silently adopt a new budget or policy for historical work.
