# Durable document storage

Task 2B owns the private application SQLite database and source files. `DocumentStore` accepts inspected PDF bytes and page count; PDF parsing belongs to `PdfInspector`. The authenticated route supplies the owner. `Document`, `Run`, and `DocumentDetail` remain the shared domain contracts.

1. Validate the admission shape, filename, page count and bytes against the inspector's shared `PdfLimits`, pipeline version, and complete run configuration. Snapshot bytes and configuration before hashing. An owner-scoped idempotency key identifies the full validated filename, source hash, page count, pipeline, and configuration, independent of object property order. Exact repeats return the original IDs. A changed request conflicts, including after terminal completion. An inactive document stays concealed.
2. Write only generated document directories and `source.pdf` under the private data directory. Use exclusive temporary files, file sync, atomic rename, directory sync, and restrictive modes. Never use the upload name as a path. Allow at most two admissions to stage files concurrently. Finish the file before the SQLite admission transaction. The transaction writes the document, run, admission receipt, and outbox together. A rejected admission schedules no work and removes its new files.
3. SQLite owns one active run per owner and one running run globally. Queue capacity counts queued jobs only. The transaction checks capacity before inserting an outbox entry. Accepted work stays queued without a dispatcher. Admission allocates a stable unique Mastra run ID before the dispatcher starts it.
4. `claimNext` atomically claims the oldest queued run and sets its running state, opaque fencing token, worker identity, and deadline. Renewals and updates require the current token and an unexpired lease. Terminal updates remove the outbox entry. Expired running leases become interrupted and are never silently retried. Mastra owns stage order; this store only enforces the domain's run transitions.
5. The supported deployment is one application process on one private persistent volume. Startup reconciliation runs before admission opens. It removes known crash temporary paths and unreferenced document directories, and marks queued/running records with missing or corrupt sources failed. Later `reconcile()` calls expire documents and remove inactive/orphan trees without sweeping live temporary paths or rehashing retained sources. Each tree removal rechecks durable state under the transaction lock and preserves in-process admissions. See [retention](retention.md). A crash before database commit leaves an orphan file; a crash after commit preserves accepted work. Source reads validate the saved length and hash. Database and artifact failures are typed storage failures, never successful empty data.
6. `AMUSEME_EXAMPLES_OWNER_ID` optionally names one examples owner. `readableOwner(reader, id)` returns the document owner when the reader owns it or the owner is the examples owner, and the same not-found failure otherwise; read routes use that owner. `listExamples` returns the examples owner's active documents to every other reader. Delete, retry, admission and rating writes still use the session user, so a non-owner gets not-found. `AMUSEME_UPLOADS_PER_USER` optionally caps admissions per non-admin owner. The count is every document row the owner ever created, so deleted and expired tombstones still use a slot; the check runs before staging and again inside the admission transaction, and refusal is `forbidden`. Exact idempotent replays still return their original IDs.
7. Owner-scoped reads check identity before lifecycle. Unknown, other-owner, deleted, and expired documents all return the same not-found failure. List hides inactive documents. Deletion requires a terminal run, commits a concealed tombstone before removing files, and can finish cleanup after restart. Expiry also conceals downloads immediately; cleanup is local and does not claim to erase backups or third-party copies.
7. Kysely and libSQL are the explicit Promise SDK boundary in `src/storage/database.ts`. Effect owns transactions, scoped cleanup, filesystem work, clocks, hashing, and randomness. There are no provider calls or retries here. The application database is `application.sqlite`, separate from authentication and Mastra storage. The provider guard uses the same transaction service and `provider_attempts` migration, with its own receipt/dispatch rules. Its `provider_charges` ledger has no owner, document, or payload reference and survives deletion and expiry. Deleting private attempt payloads never refunds spent or reserved funds. Migration version 2 adds the independent ledger and explicit response-validation state without dropping existing records.

Startup also rejects a database containing provider attempts without corresponding spending-ledger entries. In particular, an older database cannot silently create a fresh allowance by migrating to the independent ledger. Existing charges require explicit budget reconciliation; the application never guesses their budget identity.

Verification uses actual local SQLite and filesystem operations. Tests cover admission replay/conflict, isolation, restart, concurrent admission/claims, queue limits, terminal fencing, expiry/deletion concealment, permissions, unsafe names, missing/corrupt sources, failed writes, and migration accounting. HTTP/browser evidence belongs to the integrating manager.
