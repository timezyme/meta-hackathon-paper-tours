# Submission preparation

1. The foundation is a mixed-origin integration frozen on October 28, 2026, containing earlier source and event-era adaptations. It is excluded from new-work claims and is not a pre-event revision. Its manifest hash and every foundation file's bytes and executable status must match the supplied inventory. It is published as a release archive; `LICENSING.md` in the submission states its license.
2. `scripts/submission/prepare.py prepare` compares each inventoried file in a specified current tree with the immutable foundation. A changed UTF-8 text file becomes line-copy, line-skip and readable UTF-8 additions in `changes.json`; any other changed file is carried whole as base64. Every new candidate file requires an explicit `--new-file` argument; unknown untracked files are not swept in. Dot-prefixed paths are rejected except `.env.example`; private and dependency directories are rejected. Missing baseline files fail rather than being silently copied. A foundation file the application removed requires an explicit `--deleted-file` argument, is refused if it still exists, and is recorded as `"deleted": true`; reconstruction removes it and leaves it out of the target inventory. The maintainer must review additions and select only authorized event work; the tool cannot determine authorship or rights.
3. Preparation creates a separate foundation ZIP and a fresh candidate directory. The candidate includes the foundation manifest, changes, explicitly selected new files, reconstruction script, the `NEW-WORK.md` review inventory and `submission.json`. It also holds reading views of every changed text file: `changed/<path>` is the full event version and `diffs/<path>.diff` a Git-style unified diff against the foundation, so foundation context and deleted lines appear there. A changed `.gitignore` or `.gitattributes` gets only a diff, because Git would apply a full copy to the views folder. Changed binary files get no view and are listed in `NEW-WORK.md`. `submission.json` records each view's hash, size and mode under `views`. Views have their own, larger limits, because a diff holds both versions of a file; preparation applies every limit reconstruction applies, so it never writes a candidate that reconstruction would refuse. The candidate writes no ignore file, so a fresh Git clone of it holds every file. Judge access and publication are not established by preparation.
4. `reconstruct` refuses an existing output, checks inventory and archive members, rejects duplicate, traversal, symlink, encrypted, unexpected, oversized or mismatched members, applies changes in a temporary directory and verifies every final file's hash, size and executable status. It builds only from the archive, `changes.json` and `new/`, never from the views. It then regenerates every view from what it built and refuses the result unless the view inventory, each recorded hash and each view file all match. It never reads application data or changes a budget. A failed reconstruction must not leave a successful output.
5. Verify with `python3 -I -m unittest discover -s tests/submission -v`. Each guard's test asserts that guard's own message, and negative tests create the files they expect to be refused. Before delivery, also reconstruct the actual intended tree, compare its complete inventoried bytes and modes, review the generated candidate (including `changed/` and `diffs/`) for private content and origin, and run applicable application checks and Chrome verification from the reconstructed tree. Fixture-only verification does not prove live service access.
