# Muse review

Covers: agent:extraction-review, agent:page-check-review, agent:headings-review, agent:figures-review, agent:guide-review, agent:figures-crop-review

1. Every Muse stage unit (extraction page, checked page, the heading pass, one figure, the guide) runs inside its existing workflow step. When the stage check rejects the unit's answer, the stage's reviewer runs next for that unit. No reviewer call is made for an answer that passes, so a clean run costs nothing extra.
2. Reviewers are registered Mastra agents with stable IDs `<stage>-review` (name "AmuseMe <stage> review"). They are created and registered with the stage agents in `makeMetaAgentBoundary` and accept only the same adapter-issued permit, bound to the reviewer's own agent ID. They keep one step, no tools, no memory and zero model, processor and transport retries.
3. The check is the stage validator plus checks that would otherwise fail a later step: page checks must not fix or join a block that an earlier page's check already used. Validators report concrete problems by block, figure or quote. The guard stores the first problems as the rejection message.
4. The reviewer gets what a human editor would: the unit's original evidence exactly as sent (text and, for extraction, page checking and figures, the image), then `museReview` with the original stage brief, the rejected answer, its SHA-256 and the problem list. It answers in the stage's schema. Its system prompt is the versioned brief `<stage>-review` / `amuseme-1` from `src/domain/prompt-templates.ts`; the stage's model, effort and output limit are unchanged.
5. A review is a normal guarded attempt with the `review` retry tag: it reserves the stage's maximum charge, gets a receipt, counts toward the run cap, the authorized budget and `maxProviderAttempts` for the unit, and keeps the reservation of the remaining mandatory stages free. The round and rejected-answer hash are part of the request, so the fingerprint is deterministic. Resume and retry replay saved answers and saved rejections (`ProviderGuard.rejected`) without another paid call. Existing fingerprints are unchanged, so no pipeline or prompt version changed.
6. At most two review rounds run per unit. When review cannot run (attempt allowance, budget, preflight or transient provider failure) or its answer is still invalid, the stage's safe fallback applies. Unknown completion, conflicts and storage failures still stop the run.
7. Fallbacks keep source text intact and downstream validation strict:
   - page checking keeps only the fixes and joins that pass every check alone, at worst no changes;
   - headings keep the extractor's classification (heading marks give the level, paragraphs stay paragraphs, one level-1 title);
   - a figure is published without an AI description;
   - the document is published without a reading guide;
   - extraction has no independent text source, so a page still invalid after review fails the run.
8. `processing-report.json` lists each review under optional `museReviews`: stage, reviewer agent, units, problems, rounds, attempt IDs, outcome `corrected` or `fallback`, and the fallback used. Each non-figure fallback also adds a `provider-failure` issue, so the run is `succeeded-with-issues`. Publication accepts a page without an accepted page-check receipt, or a configured guide that is missing, only when such a fallback is recorded. Older reports without the field still decode.
9. Tests cover correction on review, exhausted review, an attempt-limited fallback without review, zero-call replay of saved reviews, and the report records.
10. Reviewer briefs are versioned with their stage prompt. Page-check prompt `amuseme-3` uses page-check reviewer brief `amuseme-2`, which may add furniture classifications so a valid join across a running head is kept (see [page checking](page-check.md)). Runs configured with page-check `amuseme-2` keep the `amuseme-1` brief and its exact requests, so their saved reviews replay unchanged. All other briefs remain `amuseme-1`.

## Figure crop review

11. Validation cannot tell whether a crop holds the whole figure, so every figure with a cropped region gets a crop review in the extraction step, before any later step sees the figure. The registered agent `figures-crop-review` ("AmuseMe figures crop review") gets the full rendered page image, the crop image and a JSON object with the page size, the figure's label and caption and the crop box in page pixels. It answers the strict schema `{verdict: "confirmed" | "corrected", box: {x, y, width, height} | null}` under the versioned prompt `figures-crop-review`. The run configuration's `figureCropPromptVersion` selects the prompt. New runs use `amuseme-2`: the JSON also lists the page's other proposed figure regions (`otherFigures`), and the prompt asks for this one figure only, never the whole page, its title or another figure. Runs without the key, including retries of earlier runs, keep `amuseme-1` and its exact requests, so their saved reviews replay unchanged.
12. A corrected box is accepted only when it lies inside the rendered page, is at least 24 pixels wide and high, and overlaps the box under review by at least 25% of the smaller box. Each round measures from the box it was shown, so a proposal that missed its figure can reach it over two rounds (OSHA run `322b8820`: proposals sat up to 175 px above their pictograms, and measuring from the first proposal capped every move near 110 px). It is also rejected when it covers half the page or more, or half or more of another figure's region on the page, unless the proposed box already did (see [figures](figures.md) rules 8–9). A corrected box equal to the current box counts as confirmation. The guard rejects any other answer, and its problems go to the next round. Saved answers are checked again under these rules when they are replayed. An accepted correction is cropped through the existing integer page-crop path and reviewed again.
13. At most two crop-review calls run per figure. A confirmation ends review with outcome `confirmed` (first box) or `corrected` (a corrected box confirmed). When review ends without a confirmation after a correction, neither box is trusted: the published box is the smallest one holding both the extractor's proposal and the last valid correction, so no part either saw is cut off, with outcome `unconfirmed`. If that box would break the half-page or half-figure limit, the last valid correction is kept instead. Evidence (November 2 runs): unconfirmed corrections cut off three NASA step drawings (run `f95005a0`) and the top of patent FIG. 6 (run `cd846c77`) whose proposals were whole, while on ten other patent figures the proposal was the clipped one. When review cannot run (attempt allowance, budget, preflight, request size or transient provider failure), the extractor's box is kept with outcome `not-reviewed`. Both add a located `figure-crop-unconfirmed` issue, so the run is `succeeded-with-issues`. Unknown completion, conflicts and storage failures still stop the run.
14. A crop review is a normal guarded `figures` attempt with task `figure-crop`. The task is part of its unit key and fingerprint, so it never collides with the figure's description attempt; requests without a task keep their existing keys and fingerprints. The first call reserves the figures stage maximum and keeps the remaining mandatory reservations free through the attempt's headroom; the second is a `review` retry of the first. Each call gets a receipt, counts toward the run cap, the authorized budget and the unit's attempts, and replays on resume without another paid call.
15. `processing-report.json` lists each reviewed crop under optional `figureCrops`: figure, page, agent, outcome, rounds, attempt IDs, proposed and final boxes, problems and warning. Publication requires the final box to match the published figure region, every attempt to be a crop-review receipt for that figure, and an issue for every warning. Older reports without the field still decode.
16. The figures on one page are cropped and reviewed at most three at a time (`figureChainLimit`, never more than the guard's `maxConcurrentCalls`); each figure's rounds stay in order. Requests depend only on the page and that figure's proposal and answers, so they and their fingerprints match a one-at-a-time run, and results are saved in block order. When one figure fails, no new figure starts; figures already running finish, so no paid call is abandoned, and the step then fails with the first failure in block order. Completed calls replay on resume or retry; an interrupted call needs an acknowledged retry, as before. Pages are still extracted one after another, and page checks stay sequential because each depends on earlier pages.
